# PTX track: hand-written GPU assembly inside tensor-ash's Vulkan command buffers

Branch `campaign/ptx` (worktree `~/repos/tensor-ash-wt/c-ptx`), 2026-09-26.
Everything experimental ran on louise-pc's RTX 4060 first; the RTX 3070
only got binaries/kernels that had already passed there (short batches,
`gpu3070` lock).

## Verdict

**Feasible, stable, and worth a backend.**  The NVIDIA proprietary
driver's `VK_NV_cuda_kernel_launch` (rev 2) JIT-compiles PTX (and
accepts cubins/fatbins) and records CUDA kernel launches into ordinary
Vulkan command buffers, addressed with Vulkan buffer-device-addresses.
Ordinary compute pipeline barriers order those launches against Vulkan
dispatches in both directions (and CUDA->CUDA), GPU timestamps bracket
them, launch parameters are captured at record time, the bound Vulkan
compute state survives a launch, and dynamic shared memory up to 99 KiB
works with no attribute call.  Nothing crashed or hung on either GPU.

What it buys, measured (4060 = louise-pc, 3070 = desktop; ratios are
interleaved same-process A/Bs against tensor-ash's own route):

| lever | 4060 | 3070 |
|---|---|---|
| **TinyLlama-1.1B f16 pp512, PTX f16-accumulate route** (`ML_PTX_GEMM=f16`) vs tensor-ash base | **1.36-1.38x** (12.9k -> 17.5-17.9k t/s) | **1.63x** (15.4k -> 24.3-25.4k t/s) |
| same vs llama.cpp b9503 CUDA (same accumulate precision: cuBLAS `COMPUTE_16F`) | **1.36x** (same-day 12.9k) | ~1.5x vs the Sept scoreboard 16.7k (same-day re-measure blocked by the desktop embargo) |
| pp512 with `ML_PTX_GEMM=f16p` (f16-rate mma, f32 promotion per k-tile; 5-8x lower error than f16 acc) | 1.16x (BK=32 kernel; BK=64 pick pending) | - |
| f16 tensor-core GEMM, f16 accumulate, vs coopmat1 on the same f16 A/B/C (prefill shapes + squares) | 1.43-1.79x (40-48 TF/s) = 80-94% of cuBLAS 16F | 1.50-1.97x (48-68 TF/s) = 75-100% of cuBLAS 16F |
| same, f32 accumulate (numerics identical to coopmat1) | 1.00-1.12x | 0.98-1.13x |
| f32 SIMT SGEMM with a 3/4-stage `cp.async` pipeline vs tensor-ash's best GLSL route | 0.86-1.08x (ties on large) | 0.73-1.01x (ties at 2048/4096) |

Token-exact: 32 greedy tokens after a 128-token (a16-path) prompt are
identical for base, f32, f16p and f16 routes; the a16 correctness suite
passes 13/13 through the f32-accumulate PTX route.

The central finding is not "PTX beats GLSL" in general - with f32
accumulation both sit at the GeForce f32-accumulate tensor ceiling, and
f32 SIMT is not limited by the missing `cp.async` - it is that **the
whole llama.cpp prefill gap was f16 accumulation**: tensor-ash coopmat1
(27-29 TF/s on the 4060) already equals cuBLAS `COMPUTE_32F` (27.6-30.8),
and today's campaign base already matches llama.cpp CUDA pp512 on the
4060 (12.87k vs 12.89k), while cuBLAS `COMPUTE_16F` - the path llama.cpp
b9503 takes for f16 weights - runs at 42-55 TF/s.  Vulkan's coopmat
could express f16 accumulation too, but PTX gives the `mma.sync` +
`ldmatrix` + `cp.async` pipeline that reaches 80-100% of cuBLAS with it,
plus a promoted variant (f16p) that cuBLAS does not have.

## Setup

* RTX 4060 (AD107, sm_89, 24 SMs), driver 595.80, louise-pc.
  RTX 3070 (GA104, sm_86, 46 SMs), driver 595.99, desktop.
* Both expose `VK_NV_cuda_kernel_launch` rev 2 with
  `cudaKernelLaunchFeatures = VK_TRUE`, `computeCapability` (8,9) / (8,6),
  plus `VK_NVX_binary_import`.
* PTX generated by CUDA 12.9 `nvcc -ptx -arch=sm_80` from checked-in
  CUDA C with inline PTX (`ptx/*.cu`, `ptx/build.sh`); the `.ptx` text is
  checked in and embedded (`src/ptx/kernels.rs`), so tensor-ash builds
  with no CUDA toolkit.  The driver JITs it for the real GPU.
* Harness: `ml_bench ptx <probe|smem|sync|state|overhead|dump|sgemm|hgemm>`
  (`tools/ml-bench/src/bench/ptx.rs`), requires `ML_PTX=1`.  GEMM timing
  = one GEMM per submission bracketed by TOP_OF_PIPE / BOTTOM_OF_PIPE
  timestamps (the executor's own convention), ~300 ms burn-in, then
  `ML_ROUNDS=7` interleaved rounds x `ML_ITERS=5` per side with the side
  order alternating per round, medians reported.  Every kernel is
  validated against an f64 CPU reference on 512 sampled outputs (plus
  corners) *before* it is timed; a failing kernel is reported and never
  timed.
* cuBLAS references: `benchmarks/cublas_bench/cublas_bench` (FP32,
  pedantic) and `benchmarks/cublas_bench/cublas_hgemm_bench.cu`
  (new: `cublasGemmEx` with f16 A/B, `COMPUTE_16F` and `COMPUTE_32F`, TN =
  llama.cpp's exact call and NN = tensor-ash's layout, CUDA events).

## 2. Ordering / visibility

`ml_bench ptx sync` (defaults: n = 16M u32 = 64 MiB per buffer, 32
ping-pong steps per command buffer, 3 trials).  Each step reads buffer
`s%2` and writes the other (RAW on the new data, WAR on the old), with
distinct affine constants per step; the final buffer is compared with
the CPU composition.  The Vulkan twin (`shaders/ptx_probe_affine.comp`)
walks the buffer in *reverse*, the CUDA `probe_affine` forward, and
`CudaAlt` alternates CUDA forward/reverse kernels, so a missing
dependency races on exactly the elements the producer writes last.

Mismatches (sum over 3 trials x 16.8M elements; GPU ms per 32-step chain):

| chain | barrier between steps | 4060 mismatches | 4060 ms | 3070 mismatches | 3070 ms |
|---|---|---:|---:|---:|---:|
| Vulkan<->CUDA alternating | `COMPUTE->COMPUTE`, `SHADER_WRITE -> SHADER_READ\|WRITE` | 0 | 15.07 | 0 | 10.29 |
| Vulkan<->CUDA alternating | `ALL_COMMANDS`, `MEMORY_WRITE -> MEMORY_READ\|WRITE` | 0 | 15.32 | 0 | 10.33 |
| Vulkan<->CUDA alternating | `COMPUTE->COMPUTE`, execution only (no memory barrier) | 0 | 15.05 | 0 | 10.29-10.66 |
| Vulkan<->CUDA alternating | none | **74-80 K per trial** | 15.06 | **131-146 K** | 10.18 |
| CUDA fwd/rev alternating | compute barrier | 0 | - | 0 | 10.30 |
| CUDA fwd/rev alternating | none | - | - | **98-109 K** | 10.20-10.92 |
| CUDA only / Vulkan only (same direction) | none | 0 (no power: same traversal order) | 16.6 | 0 | 10.3-10.5 |

Conclusions:

1. A normal compute->compute pipeline barrier orders a CUDA launch after a
   Vulkan dispatch, a Vulkan dispatch after a CUDA launch, and a CUDA
   launch after a CUDA launch - with full memory visibility, at 64 MiB
   and 32 dependent steps per command buffer.  No events, semaphores or
   submission splits are needed; the executor's existing
   `record_compute_to_compute_barrier` / `HazardCursor` logic applies
   unchanged.
2. Without a barrier, CUDA launches do overlap each other and Vulkan
   dispatches (tens of thousands of stale reads; see also the
   `probe_bump` race and the `%globaltimer` overlap below), i.e. they
   are *not* implicitly serialized.
3. The execution-only barrier happened to show no stale data (NVIDIA's
   L1 is not kept dirty across grid boundaries), but the spec-correct
   form - and what the executor records - is the memory barrier.
4. Timestamps bracket CUDA work: the alternating 4060 chain moves
   32 x 128 MiB in 15.07 ms = 285 GB/s (DRAM 272 GB/s; the reverse->forward
   alternation gets 24 MB L2 reuse, which is also why it beats the
   same-direction chains at 16.6 ms = 259 GB/s); the 3070 chain is at
   417 GB/s of 448.

## 3. Launch overhead

`ml_bench ptx overhead` (256 launches per command buffer, 9 reps, median):

| variant | 4060 GPU us/launch | 3070 GPU us/launch | host us/record (4060 / 3070) |
|---|---:|---:|---:|
| CUDA `probe_bump` (1 CTA x 32 thr), no barrier | 0.117 | 0.127 | 0.36 / 1.10 |
| CUDA, compute barrier between launches | **1.47** | **1.70** | 0.75 / 1.89 |
| Vulkan 1-workgroup dispatch (bind + push + dispatch), no barrier | 0.297 | 0.203 | 0.35 / 1.02 |
| Vulkan dispatch, compute barrier between | **0.86** | **1.05** | 0.79 / 2.07 |

* A *dependent* CUDA launch costs ~0.6 us more GPU time than a dependent
  Vulkan dispatch (1.47 vs 0.86 us on the 4060, 1.70 vs 1.05 on the
  3070).  Irrelevant for GEMMs (>= 100 us); relevant for decode chains of
  tiny kernels, where PTX should only replace kernels that win by more.
* Independent CUDA launches are cheaper than Vulkan dispatches and run
  concurrently: 256 unsynchronized non-atomic `counter += 1` launches
  left the counter at 168 (4060) / 104 (3070); with barriers it is 256.
* `%globaltimer` stamps of two back-to-back spinning launches: no
  barrier -> both start at the same tick (overlap); with a barrier the
  second starts 1.0 us (4060) / 2.1 us (3070) after the first ends.

## 4. f32 SGEMM with a cp.async pipeline

`ptx/sgemm.cu`: CTA 128x128, 256 threads (8 warps 4x2, warp tile 32x64,
thread tile 8x8), BK 8 or 16, 2-4 stage `cp.async.cg` (16 B, `v4`) or
`cp.async.ca` (4 B, `s1`, any shape) pipeline.  A stays `[m][k]` in
shared memory (cp.async cannot transpose); a thread's 8 rows are
interleaved (`i*4 + ty`) and rows are padded to BK+4 floats so each
LDS.128 of A hits 4 distinct bank groups.  128 registers, 2 CTAs/SM,
~85% FFMA density in the main loop.

**Finding (negative):** a real multi-stage `cp.async` pipeline - the
primitive every GLSL smem-pipeline experiment lacked - does *not* by
itself close the f32 gap to cuBLAS.  The PTX kernel ties the tuned GLSL
BDA_V4 kernels on large squares on both GPUs and loses on small shapes
(one 128x128 tile shape vs tensor-ash's tile family).  On the 4060
everyone (tensor-ash, PTX, cuBLAS) sits at ~8.4-8.7 TF/s at 4096^3 - the
board is power-limited there (tensor-ash min 14.25 ms vs median 16.2
ms).  The remaining 3070 gap to cuBLAS (12.1 vs 13.5 TF/s) is below
PTX: register-bank/reuse scheduling in SASS.  The path to that level now
exists (the driver accepts cubins, so hand-scheduled SASS can be
assembled offline and shipped), but it is a different project.
Driver-JIT SASS == nvcc 12.9 SASS here, so no JIT penalty either way.

## 5. f16 tensor-core GEMM (mma.sync + ldmatrix + cp.async)

`ptx/hgemm.cu`: `mma.sync.aligned.m16n8k16.row.col`, A fragments via
`ldmatrix.x4`, B fragments via `ldmatrix.x4.trans` straight from the
`[K][N]` weight layout, XOR-swizzled 16-byte chunks (conflict-free
ldmatrix phases), 2-4 stage `cp.async.cg` pipeline, dynamic shared
memory up to 72 KiB.  Operand contract = tensor-ash's a16 route (the
one llama prefill uses): f16 A (activations), f16 B `[K][N]`, f16 C;
`_o32` variants store f32.  Accumulation variants:

* `f32` - `mma ...f32.f16.f16.f32` (numerics class of coopmat1).
* `f16` - `mma ...f16.f16.f16.f16`, 2x tensor throughput on GeForce.
* `f16p` (round 2) - f16-rate mma within one BK=32 k-tile, promoted into
  f32 registers after every k-tile.

### What llama.cpp actually does (b9503)

`ggml_cuda_mul_mat` sends f16-weight GEMMs with more than 16 tokens
(`ggml_cuda_should_use_mmf` returns false for `src1_ncols > 16`) to
`ggml_cuda_op_mul_mat_cublas`, which on NVIDIA Ampere/Ada (not Volta,
not CDNA/RDNA4, `GGML_PREC_DEFAULT`) converts the activations to f16 and
calls `cublasGemmEx(..., CUDA_R_16F, ..., CUBLAS_COMPUTE_16F,
CUBLAS_GEMM_DEFAULT_TENSOR_OP)` with an f16 C, then converts C to f32
(`ggml/src/ggml-cuda/ggml-cuda.cu`, commit e3ba22d, lines ~1690-1745).
So llama.cpp's prefill runs on **f16-accumulate** tensor cores; the
comparison below against cuBLAS `COMPUTE_16F` and our `f16` kernels is
the like-for-like one, and tensor-ash coopmat1 vs cuBLAS `COMPUTE_32F`
is the other like-for-like pair.

## 7. Design proposal: a PTX accelerator backend

Status on this branch: the pieces below marked (done) exist as opt-in
code; the rest is the proposal.

1. **Runtime probe (done).** `VulkanContext` enables
   `VK_NV_cuda_kernel_launch` (+ `VK_NVX_binary_import`) only when
   `ML_PTX=1` and the feature bit is set; `ML_NO_PTX=1` always vetoes;
   device creation is byte-identical otherwise.  Exposed as
   `ctx.cuda_launch`, `ctx.nvx_binary_import`,
   `ctx.cuda_compute_capability`.  Proposal: once the route has a GPU
   gate in `ml_bench thesis`, flip to default-on for NVIDIA proprietary
   drivers with cc >= 8.0 and keep `ML_NO_PTX=1` as the kill switch.
2. **Modules (done).** PTX text is embedded (no toolkit at build time).
   `CudaModule::from_ptx_cached` persists the driver-compiled cubin
   (`vkGetCudaModuleCacheNV`) under
   `~/.cache/tensor-ash/ptx_<label>_v<vendor>_<device>_d<driver>_<hash>.cubin`;
   a cold JIT of the GEMM module costs 0.4-0.7 s, a cached load ~0.1 ms.
   Any load/JIT failure logs and leaves the Vulkan kernels in charge
   (GLSL fallback is the default path, not an error path).  Lowering
   the emitted `.version` (nvcc 12.9 writes 8.8) to the lowest ISA the
   kernels need would widen the driver range.
3. **Routing (done, opt-in).** `ML_PTX_GEMM=f32|f16|f16p` builds a
   `PtxRoute` in `MatmulPipeline`; `record_one_matmul` asks
   `route.select(m, n, k)` for a16 matmuls (f16 A/B/C, batch 1, plain
   `alpha*A*B`, no fused epilogue/normed-A/store) and records
   `vkCmdCudaLaunchKernelNV` instead of bind + push + dispatch.  The
   current tile pick is a two-line SM-count heuristic
   (`VK_NV_shader_sm_builtins`); the proposal is to make PTX entries
   ordinary candidates of the existing measured tuner (`ML_TUNE`), keyed
   by the same `TuneKey`, so the per-device winner (the 4060 and 3070
   disagree - 24 MB vs 4 MB L2) is measured, not guessed.  Caveat today:
   with the route on, `ML_TUNE=1` measurements of a16 coopmat candidates
   actually time the PTX kernel (the recorder substitutes it), so tune
   with the route off until PTX entries are first-class candidates.
4. **Graphs / PreparedOps (done by construction).** Because (a) compute
   barriers order CUDA launches both ways, (b) params are captured at
   record time, and (c) bound Vulkan state survives a launch, a PTX
   kernel is just another recorded op: `HazardCursor` barrier placement,
   graph census, and prepared replay work unchanged.  Buffers are BDA
   addresses, which tensor-ash already caches per `Buffer`.
5. **Precision policy.** f16 accumulation must stay an explicit choice
   (it is ~10x noisier).  Proposal: a per-op precision flag mirroring
   ggml's `GGML_PREC_DEFAULT/F32` - llama prefill projections may opt
   into `f16`/`f16p`, attention scores and anything reduction-sensitive
   stay f32.  `f16p` (f16-rate mma, per-k-tile f32 promotion) is the
   candidate default if its error stays near f32's (round 2).
6. **Epilogues / fusion next.** The Vulkan route fuses bias, activation,
   residual and RoPE stores; the PTX kernels should grow the same
   template epilogues (cheap: registers are already in hand) before they
   replace fused paths.  Split-K for small-MN/large-K shapes (512x2048x5632
   is our weakest shape vs cuBLAS) and a TN-weight variant are the next
   kernel items; int8 `mma.m16n8k32` / int4 `m16n8k64` for the
   quantization track reuse exactly this scaffolding.
7. **SASS.** The driver accepts cubins through both extensions and
   returns its own cubin for `nvdisasm`, so a hand-scheduled SASS kernel
   can ship as a cubin blob with the PTX as fallback when the device's
   cc differs.  That is the lever left for f32 SIMT SGEMM.

## Negative results and dead ends (this track)

* **cp.async alone does not fix f32 SGEMM.**  A real 3/4-stage cp.async
  pipeline (BK 8/16, 128x128, 8x8 thread tiles, conflict-free LDS.128)
  ties tensor-ash's GLSL BDA_V4 kernels on large squares and loses on
  small/odd shapes on both GPUs; the 3070 cuBLAS gap (13.7 vs 12.1 TF/s at
  4096^3) is below PTX (SASS scheduling).  Driver-JIT SASS equals nvcc
  12.9 SASS, so there is no JIT tax to win back either.
* **f32-accumulate tensor-core GEMM has no headroom on GeForce.**  PTX
  mma.sync f32-acc is +0-13% over coopmat1; both sit at the half-rate
  f32-accumulate ceiling (4060 ~30 TF/s, 3070 ~41 TF/s; cuBLAS 32F is in
  the same place).  As an end-to-end route it is a wash (4060 pp512 0.98x).
* **Split-K** (two-stage, deterministic) did not speed up any of the
  512-row prefill shapes on either GPU; it only reduces f16-acc error.
* **8-warp 128x128, BK=64, 256x128 f16 tiles**: no general win over the
  4-warp 128x128 3-stage kernel (BK=64 helps 512x2048x2048 slightly).
* **4-stage / 64 KiB+ shared memory** hurts: one CTA per SM (s4 variants
  -10 to -25% vs s3).
