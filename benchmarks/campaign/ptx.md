# PTX track: hand-written GPU assembly inside tensor-ash's Vulkan command buffers

Branch `campaign/ptx` (worktree `~/repos/tensor-ash-wt/c-ptx`), 2026-09-26.
Everything experimental ran on louise-pc's RTX 4060 first; the RTX 3070
only got binaries/kernels that had already passed there (short batches,
`gpu3070` lock).

## Verdict

**Feasible, stable, and worth a backend.**  The NVIDIA proprietary
driver's `VK_NV_cuda_kernel_launch` (rev 2) JIT-compiles PTX (and
accepts cubins/fatbins) and records CUDA kernel launches into ordinary
Vulkan command buffers, addressed with Vulkan buffer-device-addresses.
Ordinary compute pipeline barriers order those launches against Vulkan
dispatches in both directions (and CUDA->CUDA), GPU timestamps bracket
them, launch parameters are captured at record time, the bound Vulkan
compute state survives a launch, and dynamic shared memory up to 99 KiB
works with no attribute call.  Nothing crashed or hung on either GPU.

What it buys, measured (4060 = louise-pc, 3070 = desktop; ratios are
interleaved same-process A/Bs against tensor-ash's own route):

| lever | 4060 | 3070 |
|---|---|---|
| **TinyLlama-1.1B f16 pp512, PTX f16-accumulate route** (`ML_PTX=1 ML_COOPMAT_ACC=f16`; measured as `ML_PTX_GEMM=f16`, same kernels) vs tensor-ash base | **1.39x** (12.9k -> 17.8-17.9k t/s) | **1.58x** (16.1-16.2k -> 25.5-25.6k t/s) |
| same vs llama.cpp b9503 CUDA pp512, same day (same accumulate precision: cuBLAS `COMPUTE_16F`) | **1.39x** (vs 12.9k) | **1.61x** (vs 15.8k) |
| pp512 with `ML_COOPMAT_ACC=f16p` (f16-rate mma, f32 promotion per 64-K tile; GEMM error ~3-7x *lower* than llama.cpp's cuBLAS path) | **1.28x** base (16.5-16.7k t/s = 1.28x llama.cpp CUDA) | **1.35x** base (21.7-21.9k t/s = 1.38x llama.cpp CUDA) |
| f16 tensor-core GEMM, f16 accumulate, vs coopmat1 on the same f16 A/B/C (prefill shapes + squares) | 1.43-2.05x (40-53 TF/s) = 80-104% of cuBLAS 16F (4096^3 with grouped raster beats it) | 1.50-2.00x (48-70 TF/s) = 75-104% of cuBLAS 16F (2048^3/4096^3 match or beat it) |
| same, f32 accumulate (numerics identical to coopmat1) | 1.00-1.12x | 0.98-1.13x |
| f32 SIMT SGEMM with a 3/4-stage `cp.async` pipeline vs tensor-ash's best GLSL route | 0.86-1.08x (ties on large) | 0.73-1.01x (ties at 2048/4096) |

Token-exact: 32 greedy tokens after a 128-token (a16-path) prompt are
identical for base, f32, f16p and f16 routes on the 4060 and for base,
f16p and f16 on the 3070; the a16 correctness suite passes 13/13
through the f32-accumulate PTX route.

The central finding is not "PTX beats GLSL" in general - with f32
accumulation both sit at the GeForce f32-accumulate tensor ceiling, and
f32 SIMT is not limited by the missing `cp.async` - it is that **the
whole llama.cpp prefill gap was f16 accumulation**: tensor-ash coopmat1
(27-29 TF/s on the 4060) already equals cuBLAS `COMPUTE_32F` (27.6-30.8),
and today's campaign base already matches llama.cpp CUDA pp512 on the
4060 (12.87k vs 12.89k), while cuBLAS `COMPUTE_16F` - the path llama.cpp
b9503 takes for f16 weights - runs at 42-55 TF/s.  Vulkan's coopmat
could express f16 accumulation too, but PTX gives the `mma.sync` +
`ldmatrix` + `cp.async` pipeline that reaches 80-100% of cuBLAS with it,
plus a promoted variant (f16p) that cuBLAS does not have.

## Setup

* RTX 4060 (AD107, sm_89, 24 SMs), driver 595.80, louise-pc.
  RTX 3070 (GA104, sm_86, 46 SMs), driver 595.99, desktop.
* Both expose `VK_NV_cuda_kernel_launch` rev 2 with
  `cudaKernelLaunchFeatures = VK_TRUE`, `computeCapability` (8,9) / (8,6),
  plus `VK_NVX_binary_import`.
* PTX generated by CUDA 12.9 `nvcc -ptx -arch=sm_80` from checked-in
  CUDA C with inline PTX (`ptx/*.cu`, `ptx/build.sh`); the `.ptx` text is
  checked in and embedded (`src/ptx/kernels.rs`), so tensor-ash builds
  with no CUDA toolkit.  The driver JITs it for the real GPU.
* Harness: `ml_bench ptx <probe|smem|sync|state|overhead|dump|sgemm|hgemm>`
  (`tools/ml-bench/src/bench/ptx.rs`), requires `ML_PTX=1`.  GEMM timing
  = one GEMM per submission bracketed by TOP_OF_PIPE / BOTTOM_OF_PIPE
  timestamps (the executor's own convention), ~300 ms burn-in, then
  `ML_ROUNDS=7` interleaved rounds x `ML_ITERS=5` per side with the side
  order alternating per round, medians reported.  Every kernel is
  validated against an f64 CPU reference on 512 sampled outputs (plus
  corners) *before* it is timed; a failing kernel is reported and never
  timed.
* cuBLAS references: `benchmarks/cublas_bench/cublas_bench` (FP32,
  pedantic) and `benchmarks/cublas_bench/cublas_hgemm_bench.cu`
  (new: `cublasGemmEx` with f16 A/B, `COMPUTE_16F` and `COMPUTE_32F`, TN =
  llama.cpp's exact call and NN = tensor-ash's layout, CUDA events).

## 2. Ordering / visibility

`ml_bench ptx sync` (defaults: n = 16M u32 = 64 MiB per buffer, 32
ping-pong steps per command buffer, 3 trials).  Each step reads buffer
`s%2` and writes the other (RAW on the new data, WAR on the old), with
distinct affine constants per step; the final buffer is compared with
the CPU composition.  The Vulkan twin (`shaders/ptx_probe_affine.comp`)
walks the buffer in *reverse*, the CUDA `probe_affine` forward, and
`CudaAlt` alternates CUDA forward/reverse kernels, so a missing
dependency races on exactly the elements the producer writes last.

Mismatches per trial (of 16.8M elements; 3 trials each) and GPU ms per
32-step chain:

| chain | barrier between steps | 4060 mismatches | 4060 ms | 3070 mismatches | 3070 ms |
|---|---|---:|---:|---:|---:|
| Vulkan<->CUDA alternating | `COMPUTE->COMPUTE`, `SHADER_WRITE -> SHADER_READ\|WRITE` | 0 | 15.07 | 0 | 10.29 |
| Vulkan<->CUDA alternating | `ALL_COMMANDS`, `MEMORY_WRITE -> MEMORY_READ\|WRITE` | 0 | 15.32 | 0 | 10.33 |
| Vulkan<->CUDA alternating | `COMPUTE->COMPUTE`, execution only (no memory barrier) | 0 | 15.05 | 0 | 10.29-10.66 |
| Vulkan<->CUDA alternating | none | **74-85 K** | 15.06 | **131-146 K** | 10.18 |
| CUDA fwd/rev alternating | compute barrier (also ALL_COMMANDS, exec-only: 0) | 0 | 15.08 | 0 | 10.30 |
| CUDA fwd/rev alternating | none | **68-76 K** | 15.08 | **98-109 K** | 10.20-10.92 |
| CUDA only / Vulkan only (same direction) | none | 0 (no power: same traversal order) | 16.6 | 0 | 10.3-10.5 |

Conclusions:

1. A normal compute->compute pipeline barrier orders a CUDA launch after a
   Vulkan dispatch, a Vulkan dispatch after a CUDA launch, and a CUDA
   launch after a CUDA launch - with full memory visibility, at 64 MiB
   and 32 dependent steps per command buffer.  No events, semaphores or
   submission splits are needed; the executor's existing
   `record_compute_to_compute_barrier` / `HazardCursor` logic applies
   unchanged.
2. Without a barrier, CUDA launches do overlap each other and Vulkan
   dispatches (tens of thousands of stale reads; see also the
   `probe_bump` race and the `%globaltimer` overlap below), i.e. they
   are *not* implicitly serialized.
3. The execution-only barrier happened to show no stale data (NVIDIA's
   L1 is not kept dirty across grid boundaries), but the spec-correct
   form - and what the executor records - is the memory barrier.
4. Timestamps bracket CUDA work: the alternating 4060 chain moves
   32 x 128 MiB in 15.07 ms = 285 GB/s (DRAM 272 GB/s; the reverse->forward
   alternation gets 24 MB L2 reuse, which is also why it beats the
   same-direction chains at 16.6 ms = 259 GB/s); the 3070 chain is at
   417 GB/s of 448.

## 3. Launch overhead

`ml_bench ptx overhead` (256 launches per command buffer, 9 reps, median):

| variant | 4060 GPU us/launch | 3070 GPU us/launch | host us/record (4060 / 3070) |
|---|---:|---:|---:|
| CUDA `probe_bump` (1 CTA x 32 thr), no barrier | 0.117 | 0.127 | 0.36 / 1.10 |
| CUDA, compute barrier between launches | **1.47** | **1.70** | 0.75 / 1.89 |
| Vulkan 1-workgroup dispatch (bind + push + dispatch), no barrier | 0.297 | 0.203 | 0.35 / 1.02 |
| Vulkan dispatch, compute barrier between | **0.86** | **1.05** | 0.79 / 2.07 |

* A *dependent* CUDA launch costs ~0.6 us more GPU time than a dependent
  Vulkan dispatch (1.47 vs 0.86 us on the 4060, 1.70 vs 1.05 on the
  3070).  Irrelevant for GEMMs (>= 100 us); relevant for decode chains of
  tiny kernels, where PTX should only replace kernels that win by more.
* Independent CUDA launches are cheaper than Vulkan dispatches and run
  concurrently: 256 unsynchronized non-atomic `counter += 1` launches
  left the counter at 168 (4060) / 104 (3070); with barriers it is 256.
* `%globaltimer` stamps of two back-to-back spinning launches: no
  barrier -> both start at the same tick (overlap); with a barrier the
  second starts 1.0 us (4060) / 2.1 us (3070) after the first ends.

## 4. f32 SGEMM with a cp.async pipeline

`ptx/sgemm.cu`: CTA 128x128, 256 threads (8 warps 4x2, warp tile 32x64,
thread tile 8x8), BK 8 or 16, 2-4 stage `cp.async.cg` (16 B, `v4`) or
`cp.async.ca` (4 B, `s1`, any shape) pipeline.  A stays `[m][k]` in
shared memory (cp.async cannot transpose); a thread's 8 rows are
interleaved (`i*4 + ty`) and rows are padded to BK+4 floats so each
LDS.128 of A hits 4 distinct bank groups.  128 registers, 2 CTAs/SM,
~85% FFMA density in the main loop.

**Finding (negative):** a real multi-stage `cp.async` pipeline - the
primitive every GLSL smem-pipeline experiment lacked - does *not* by
itself close the f32 gap to cuBLAS.  The PTX kernel ties the tuned GLSL
BDA_V4 kernels on large squares on both GPUs and loses on small shapes
(one 128x128 tile shape vs tensor-ash's tile family).  On the 4060
everyone (tensor-ash, PTX, cuBLAS) sits at ~8.4-8.7 TF/s at 4096^3 - the
board is power-limited there (tensor-ash min 14.25 ms vs median 16.2
ms).  The remaining 3070 gap to cuBLAS (12.1 vs 13.4-13.7 TF/s) is below
PTX: register-bank/reuse scheduling in SASS.  (Odd shapes are worse
still: the fully general `s1` variant uses 4-byte cp.async and scalar
stores.)  The path to that level now
exists (the driver accepts cubins, so hand-scheduled SASS can be
assembled offline and shipped), but it is a different project.
Driver-JIT SASS == nvcc 12.9 SASS here, so no JIT penalty either way.

## 5. f16 tensor-core GEMM (mma.sync + ldmatrix + cp.async)

`ptx/hgemm.cu`: `mma.sync.aligned.m16n8k16.row.col`, A fragments via
`ldmatrix.x4`, B fragments via `ldmatrix.x4.trans` straight from the
`[K][N]` weight layout, XOR-swizzled 16-byte chunks (conflict-free
ldmatrix phases), 2-4 stage `cp.async.cg` pipeline, dynamic shared
memory up to 72 KiB.  Operand contract = tensor-ash's a16 route (the
one llama prefill uses): f16 A (activations), f16 B `[K][N]`, f16 C;
`_o32` variants store f32.  Accumulation variants:

* `f32` - `mma ...f32.f16.f16.f32` (numerics class of coopmat1).
* `f16` - `mma ...f16.f16.f16.f16`, 2x tensor throughput on GeForce.
* `f16p` (round 2) - f16-rate mma within one BK (32 or 64) k-tile,
  promoted into f32 registers after every k-tile.

### What llama.cpp actually does (b9503)

`ggml_cuda_mul_mat` sends f16-weight GEMMs with more than 16 tokens
(`ggml_cuda_should_use_mmf` returns false for `src1_ncols > 16`) to
`ggml_cuda_op_mul_mat_cublas`, which on NVIDIA Ampere/Ada (not Volta,
not CDNA/RDNA4, `GGML_PREC_DEFAULT`) converts the activations to f16 and
calls `cublasGemmEx(..., CUDA_R_16F, ..., CUBLAS_COMPUTE_16F,
CUBLAS_GEMM_DEFAULT_TENSOR_OP)` with an f16 C, then converts C to f32
(`ggml/src/ggml-cuda/ggml-cuda.cu`, commit e3ba22d, lines ~1690-1745).
So llama.cpp's prefill runs on **f16-accumulate** tensor cores; the
comparison below against cuBLAS `COMPUTE_16F` and our `f16` kernels is
the like-for-like one, and tensor-ash coopmat1 vs cuBLAS `COMPUTE_32F`
is the other like-for-like pair.

## 6. Round 2 kernels, split-K, f16p, and end-to-end prefill

### Tile variants (round 2)

Added 8-warp 128x128 (warp tiles 64x32 / 32x64), BK=64 two-stage
variants, 256x128, and a deterministic two-stage split-K (f32 partial
planes + an f16 reduce kernel).  Best f16-accumulate kernel per shape
(TF/s; ratio vs tensor-ash coopmat1 in the same process; share of the
best cuBLAS `COMPUTE_16F` layout):

| shape | 4060 best (kernel) | vs TA | vs cuBLAS 16F | 3070 best (kernel) | vs TA | vs cuBLAS 16F |
|---|---|---:|---:|---|---:|---:|
| 512x2048x2048 | 41.0 (128x64_k64_s2) | 1.47x | 89% | 54.0 (128x64_k64_s2) | 1.62x | 86% |
| 512x5632x2048 | 46.0 (128x128_s3) | 1.61x | 93% | 65.2 (128x128_s3) | 1.82x | 97% |
| 512x2048x5632 | 43.2 (128x128_s3) | 1.48x | 88% | 53.4 (128x128_s3) | 1.58x | 75% |
| 2048^3 | 48.1 (128x128_s3) | 1.79x | 94% | 66.3 (128x64_k64_s2) | 1.96x | 99% |

* The plain 4-warp 128x128 / 3-stage kernel stays the best general pick;
  8-warp CTAs and BK=64 help only on the 512x2048 shapes (and not
  reliably), 256x128 loses everywhere (one CTA/SM).  On the 3070 the PTX
  f16-acc kernel matches cuBLAS `COMPUTE_16F` at 2048^3 and 4096^3.
* **Split-K did not pay** on either GPU for these shapes (best split
  results: 4060 512x2048x5632 41.0 vs 43.2 unsplit; 3070 53.1 vs 53.4);
  it does lower f16-accumulate error (fewer terms per f16 chain:
  2.41e-3 -> 1.66e-3 / 1.36e-3 / 1.13e-3 rel-RMS for 2/3/4 splits at
  K=2048).  The weak 512x2048x5632 shape vs cuBLAS on the 3070 stays open.
* f32 accumulate: the 8-warp 128x128 f32 kernel is +6-7% over coopmat1
  at 2048^3/4096^3 on the 4060, below 64x64_s4 / 128x128_s3 elsewhere.

|---|---|---|---|---|
| 512x5632x2048 | 46.2 -> 46.7 | 35.9 -> 37.2 | 27.5 -> 27.2 | 49.9 / 46.3 |

## 7. The PTX backend as it lands (merge-ready, 2026-09-27)

Everything in this section is implemented on `campaign/ptx`; the
closing list is what remains a proposal.

### 7a. Two knobs: precision (policy) and backend

Precision is one policy for every f16 tensor-core GEMM backend, shared
verbatim with `campaign/f16acc` (its §9c "unified API"):

* `tensor_ash::CoopmatAcc { F32, F16, F16Promote }`
  (`src/pipeline/precision.rs`, byte-identical to f16acc's file),
  per executor: `ExecutorConfig::coopmat_acc` (default `F32`);
  `Executor::new` reads `ML_COOPMAT_ACC=f32|f16|f16p` (`promote` alias;
  invalid value = error).  `Executor::coopmat_acc()` reports the
  *effective* class.  Never a tuner or heuristic choice.
* Class contracts: `F32` = f32 accumulation end to end; `F16` = f16
  accumulation (cuBLAS `COMPUTE_16F` numerics); `F16Promote` = f16
  partials over at most 128 K promoted into f32.  The PTX kernels
  qualify: `ta_hgemm_f16p_128x64_k64_s2` promotes every 64 K, the
  grouped `ta_hgemm_f16p_128x64_s3_g8` every 32 K.
* A class nobody on the device can serve degrades to `F32` **with a
  warning** (on this branch: no PTX route; after the merge: no PTX route
  *and* no f16-accumulator coopmat configuration).  A served class that
  a particular op cannot take (fused epilogue, accumulate, batch > 1,
  N or K not a multiple of 8, unaligned address) runs that op at f32:
  the policy is a permission, never a silent downgrade.

The backend is a separate, device-level decision:

| knob | values | effect |
|---|---|---|
| `ML_PTX=1` | unset (default) / `1` | request `VK_NV_cuda_kernel_launch` at context creation |
| `ML_NO_PTX=1` | kill switch | always wins over `ML_PTX` |
| `ML_PTX_GEMM` | `on` = `auto` (default), `all`, `off` | which classes the PTX a16 route serves: `on` = `F16` + `F16Promote`; `all` adds `F32`; `off` loads no module |
| `ML_PTX_GEMM` (deprecated) | `f32` / `f16` / `f16p` | one release: `all` / `on` / `on`, and the class for env-built executors when `ML_COOPMAT_ACC` is unset, with a deprecation warning (every command logged below still reproduces) |
| `ML_PTX_GEMM_KERNEL` | an hgemm entry | forces that kernel for ops whose policy equals its class |

Rust API: `MatmulPipeline::{ptx_gemm_mode, set_ptx_gemm_mode,
ptx_serves, ptx_a16_kernel(acc, m, n, k)}`, `tensor_ash::ptx::{PtxGemmMode,
route_kernel_name, legacy_env_acc}`.  Invalid `ML_PTX_GEMM*` values are
configuration errors (`MatmulPipeline::new` fails before creating any
Vulkan object); a failed module load/JIT only logs and leaves every
matmul on its Vulkan kernel.

### 7b. Defaults and why

| setting | default | reasoning |
|---|---|---|
| accumulator policy (library, `ExecutorConfig`, `ML_COOPMAT_ACC` unset) | **`F32`** | tensor-ash's numerics contract and every test tolerance are f32 accumulation; `F32` through PTX is bit-identical to coopmat1 (test below) |
| llama-ash | **`F32`** (reads `ML_COOPMAT_ACC`) | a reference runner should reproduce the library's numerics; speed modes are one variable away |
| recommended fast mode | **`ML_COOPMAT_ACC=f16p`** (+ `ML_PTX=1`) | pp512 1.28x (4060) / 1.35x (3070) over base; GEMM error 2.2-2.4x f32-accumulate, i.e. ~3-7x *below* llama.cpp CUDA's cuBLAS path (synthetic data); on real TinyLlama activations f16acc's 128 K-chunk promote stays within 2.4x of the f16-output floor (3.6e-4 rel-RMS on the down-projection vs 1.1e-2 for `F16`) and the PTX kernel promotes 2x more often; tokens identical |
| `F16` | **opt-in only**, documented as the **llama.cpp-parity mode** | it is exactly llama.cpp b9503's prefill numerics (cuBLAS `COMPUTE_16F`), so it is the like-for-like speed comparison (1.39x / 1.61x llama.cpp CUDA) - but it is ~10x noisier than f32 accumulation, reaches 1.1% RMS / 1.76 absolute error on TinyLlama's down-projection (inputs up to 173; f16acc §3) and can overflow at 65504.  Never a default. |
| PTX backend (`ML_PTX`) | **off** | provisional (beta) NVIDIA-only extension; 0.4-1.7 s cold JIT per driver version (then a 3-5 ms cubin-cache load); device creation must stay byte-identical for everyone who did not ask |
| `ML_PTX_GEMM` with the backend on | **`on`** (F16 + F16Promote) | where PTX is the measured-fastest implementation; `F32` stays on coopmat1 because PTX f32 accumulation does not pay end to end (pp512 0.98x on the 4060; +0-13% GEMM-level) |

### 7c. Runtime probe and fallback

`ptx_gate` (`src/context/init.rs`, unit-tested) enables the extension
only when all hold: `ML_PTX=1`, not `ML_NO_PTX=1`, PCI vendor NVIDIA,
`VK_NV_cuda_kernel_launch` exposed, `cudaKernelLaunchFeatures`, compute
capability >= 8.0 (the PTX targets `sm_80`).  The feature/property
structs are chained into a query only after the extension is known to
exist, and into `VkDeviceCreateInfo` only when the gate passes, so any
other case creates exactly the device the code without PTX creates.
`VK_NVX_binary_import` rides along only when the gate passes.  The
route then needs `bufferDeviceAddress` and a successful module load
(`CudaModule::from_ptx_cached`: the driver-compiled cubin persisted
per device/driver/PTX hash); anything else logs a warning and keeps the
Vulkan kernels.  Only the hgemm module is loaded (the sgemm module is
bench-only).

### 7d. Graphs, PreparedOps, hazards

The recorder (`record_one_matmul`) gets `ptx_acc: Option<CoopmatAcc>`
from `Executor::ptx_acc()`: the executor policy on auto-routed
pipelines, `None` under an explicit `ML_KERNEL` pin and in the tuner
(which must time exactly its candidate).  When the route serves that
class for an a16 op it records `vkCmdCudaLaunchKernelNV` in place of
bind + push + dispatch - in single submissions, dependency graphs
(`HazardCursor`), mixed `ExecOp` graphs and prepared command buffers
alike.  Nothing else changes, because (§2) compute barriers order CUDA
launches both ways, parameters are captured at record time and a
launch leaves the bound Vulkan pipeline intact (`bound_pipeline`
tracking stays valid).  After the merge with f16acc the executor maps
its policy onto `_acc16`/`_acc16p` kernels; `ptx_acc` and
`CoopmatAcc::of_kernel_name(kernel.name)` then agree on auto
pipelines (f16acc's proposal reads the class from the kernel name; on
this branch alone the a16 kernels carry no class, so the policy is
passed explicitly).

### 7e. Still a proposal

1. PTX entries as first-class candidates of the measured tuner, keyed
   by `TuneKey` + class (the 4060 and 3070 disagree on tiles: 24 MB vs
   4 MB L2); today's pick is `route_kernel_name`'s SM-count heuristic.
2. Fused epilogues (bias, activation, residual, RoPE store) in the PTX
   kernels, so fused prefill ops can take the route too.
3. A pruned route module (8 entries instead of 33: ~4x less cold JIT
   and binary size; `ptx/hgemm.ptx` is 1.9 MB) and a lowered `.version`
   (nvcc 12.9 writes 8.8) to widen the driver range.
4. Default-on for NVIDIA proprietary drivers with cc >= 8.0 once an
   `ml_bench thesis` GPU gate covers the route; `ML_NO_PTX=1` stays the
   kill switch.
5. The parked round-5 kernel (`campaign/ptx-hgemm2-wip`, §8).
6. int8 `mma.m16n8k32` / int4 `m16n8k64` for the quantization track and
   hand-scheduled SASS (the driver accepts cubins) for f32 SGEMM.

## Negative results and dead ends (this track)

* **cp.async alone does not fix f32 SGEMM.**  A real 3/4-stage cp.async
  pipeline (BK 8/16, 128x128, 8x8 thread tiles, conflict-free LDS.128)
  ties tensor-ash's GLSL BDA_V4 kernels on large squares and loses on
  small/odd shapes on both GPUs; the 3070 cuBLAS gap (13.7 vs 12.1 TF/s at
  4096^3) is below PTX (SASS scheduling).  Driver-JIT SASS equals nvcc
  12.9 SASS, so there is no JIT tax to win back either.
* **f32-accumulate tensor-core GEMM has no headroom on GeForce.**  PTX
  mma.sync f32-acc is +0-13% over coopmat1; both sit at the half-rate
  f32-accumulate ceiling (4060 ~30 TF/s, 3070 ~41 TF/s; cuBLAS 32F is in
  the same place).  As an end-to-end route it is a wash (4060 pp512 0.98x).
* **Split-K** (two-stage, deterministic) did not speed up any of the
  512-row prefill shapes on either GPU; it only reduces f16-acc error.
* **8-warp 128x128, BK=64, 256x128 f16 tiles**: no general win over the
  4-warp 128x128 3-stage kernel (BK=64 helps 512x2048x2048 slightly).
* **128x128 with 4 stages (64 KiB shared)** hurts: one CTA per SM (s4
  -10 to -25% vs s3).
